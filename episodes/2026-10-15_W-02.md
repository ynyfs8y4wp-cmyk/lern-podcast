title: Pull Requests und Code Review

ANNA: Hallo und willkommen bei der Lernroute Agentifizierung. Ich bin Anna, mir gegenüber sitzt Ben, und heute geht es um zwei Begriffe, die in jedem Entwickler-Meeting fallen: Pull Request und Code Review. Ben, ich gebe zu, bei Pull Request denke ich an einen Pullover.
BEN: [laughs] Damit bist du nicht allein. Der Name ist auch wirklich etwas schief. Aber die Idee dahinter kennt jeder, der schon mal in einer Rechtsabteilung gearbeitet hat. Stell dir vor, eine Juristin ändert eine Klausel in einem Vertrag. Sie unterschreibt nicht allein, sondern schickt den Entwurf im Änderungsmodus an einen Kollegen. Der sieht jede markierte Stelle, kommentiert und sagt am Ende: Passt, geht raus. Genau das ist ein Pull Request mit Code Review.
ANNA: Also das Vier-Augen-Prinzip, nur für Software.
BEN: Ja, genau. Und um das zu verstehen, brauchen wir kurz einen Begriff aus der letzten Folge über Git: den Branch. Das ist eine eigene Arbeitskopie. Jemand kann darin ändern, ohne die gültige Fassung zu stören. Und die gültige Fassung, die heißt meistens main.
ANNA: Und der Pull Request?
BEN: Ist der offizielle Antrag. Bitte übernehmt meine Änderungen aus meinem Branch in die gültige Fassung. Gemeint ist eigentlich: Zieh meine Änderungen bitte herein. Bei manchen Werkzeugen heißt dasselbe übrigens Merge Request, das ist ehrlicher.
ANNA: Und was sieht der Kollege, der prüfen soll? Den ganzen Code?
BEN: Nein, und das ist das Schöne. Er sieht den sogenannten Diff, also nur das, was sich geändert hat. Alte Zeilen rot, neue grün. Wie der Änderungsmodus in Word. Er kann einzelne Zeilen kommentieren, Fragen stellen, und am Ende gibt er eines von drei Signalen: zustimmen, nur kommentieren oder Änderungen verlangen.
ANNA: Moment, das klingt mir jetzt sehr menschlich. Prüft da wirklich nur ein Mensch?
BEN: [thoughtful] Gute Frage. Nein. Parallel laufen automatische Prüfungen, die heißen Checks. Tests, Prüfungen der Schreibregeln im Code, Sicherheitsscans. Grüner Haken heißt bestanden, rotes Kreuz heißt durchgefallen. Und erst wenn beides stimmt, Freigabe und Checks, wird die Änderung übernommen. Viele Teams stellen in GitHub sogar ein, dass es ohne Freigabe gar nicht geht. Das nennt sich Branch Protection, also ein eingebautes Vier-Augen-Prinzip, das niemand umgehen kann.
ANNA: Mach es mal konkret. Wo merke ich das als Gruppenleiter?
BEN: Nimm euren Agenten für die Rechnungsprüfung. Der soll künftig Rechnungen bis zweitausend statt bis tausend Euro selbstständig zur Zahlung vorschlagen. Eine Entwicklerin legt einen Branch an und ändert in der Konfigurationsdatei die Grenze. Dann öffnet sie einen Pull Request mit einem Satz wie: Freigabegrenze erhöht, abgestimmt mit Finance, siehe Ticket.
ANNA: Und dann?
BEN: Dann laufen die Checks. Der Agent wird mit fünfzig alten Testrechnungen durchgespielt. Ein KI-Prüfer merkt an, dass eine Rechnung über fünfzehnhundert Euro jetzt anders behandelt wird. Ein Kollege schaut sich die Änderung an, fragt nach, ob Finance schriftlich zugestimmt hat, und gibt frei. Und Monate später kann jeder im Verlauf sehen, wer wann warum die Grenze geändert hat.
ANNA: Das ist für die Revision ja eigentlich ein Traum.
BEN: [laughs] Das ist Gold wert. Vorher hätte jemand die Grenze direkt im laufenden System geändert. Ohne zweiten Blick und ohne Spur.
ANNA: Jetzt sitzt du im Meeting. Was hörst du da?
BEN: Zum Beispiel: Kannst du mal über meinen PR drüberschauen? Heißt: Bitte prüf meine Änderung, ich brauche deine Freigabe. Oder: Der PR ist zu groß, den kann keiner sinnvoll prüfen. Heißt: Zu viel auf einmal, bitte in kleinere Häppchen teilen. Und dann der Klassiker: L G T M. Looks good to me. Sieht gut aus, freigegeben.
ANNA: Das merke ich mir. Aber jetzt kommt ja das Neue: Agenten schreiben inzwischen selbst Code.
BEN: Ja, und das verändert das ganze Bild. Agenten schreiben Pull Requests, andere Agenten machen eine erste Durchsicht. Eine Umfrage aus dem April zeigt das Problem: Mit KI entsteht mehr Code, als Teams prüfen können. Eine zitierte Auswertung kommt sogar zu dem Ergebnis, dass KI-erstellte Änderungen im Schnitt deutlich mehr Auffälligkeiten enthalten als menschliche. Das sind allerdings Zahlen eines Anbieters, die ich mit Vorsicht genießen würde.
ANNA: Und was heißt das für einen Gruppenleiter mit einem kleiner werdenden Team?
BEN: [sighs] Dass das Prüfen zum Flaschenhals werden kann. Wenn Agenten doppelt so viel schreiben, muss jemand doppelt so viel lesen. Deshalb würde ich festlegen, welche Änderungen immer ein Mensch freigeben muss. Alles, was Geldbeträge, Zugriffsrechte oder Personaldaten betrifft. Und der Pull Request ist dabei dein bestes Steuerungsinstrument, ohne dass du Code lesen musst: Jede Änderung hat einen Autor, eine Begründung und eine Freigabe.
ANNA: Dann der Merksatz.
BEN: Ein Pull Request ist der Antrag, das Review ist die zweite Unterschrift. So kommt keine Änderung ungeprüft und ohne Spur in die gültige Fassung.
ANNA: Und deine Mini-Übung: Öffne in einem GitHub-Projekt deines Teams den Reiter Pull requests, nimm den letzten abgeschlossenen und finde drei Dinge: wer ihn erstellt hat, wer ihn freigegeben hat und welche Begründung drinsteht. Bis zum nächsten Mal!
BEN: Mach's gut!
